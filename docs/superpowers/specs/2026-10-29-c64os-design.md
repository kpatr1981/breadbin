# c64os — a Unix-like operating system for the Commodore 64

Date: 2026-10-29
Status: draft, awaiting approval
Working name: **c64os** (name is a placeholder)

## Intent

A real, small Unix-like operating system for the Commodore 64. You boot it
from a disk, a kernel takes over the machine, and it starts a shell. The
user is explicit that this must be a *real OS*, not a shell that prints
canned output: the kernel manages processes, memory and files, and every
command is an actual program loaded from disk and run as a process.

The user asked for all of the following: multitasking with background
jobs, a filesystem on the 1541 disk, commands as separate executables, and
pipes.

## Goals

1. **Preemptive multitasking.** A timer interrupt drives a scheduler that
   switches between processes. `cmd &` runs in the background while the
   shell keeps accepting input. Processes block on I/O (keyboard, pipes,
   `wait`) instead of spinning.
2. **Real executables.** `ls`, `cat`, `ps`, etc. are separate files on
   disk. The shell asks the kernel to load and start them; nothing is
   built into the shell except what must be (`cd`, `exit`).
3. **Pipes and redirection.** `ls | more`, `cat a | grep x | wc`,
   `cmd > file`, `cmd >> file`, `cmd < file`. Pipes are kernel objects with
   a buffer; a reader blocks when empty, a writer blocks when full.
4. **Filesystem through the kernel.** Programs use `open/read/write/close`
   on file descriptors. Files, pipes and devices all look the same to a
   program (fd 0/1/2 = stdin/stdout/stderr).
5. **Runs on a stock C64 + 1541.** This is the baseline that must always
   work, with roughly 4–8 small processes resident.
6. **Uses an REU when present.** Detected at boot. With an REU: a fast RAM
   disk mounted at `/tmp`, and more room for processes (swapping process
   images out to the REU). Same disk image boots both configurations.

## Non-goals (v1)

- Multiple users, login, file permissions.
- Memory protection — the 6502 has no MMU, so a buggy program can crash the
  system. Accepted.
- Full POSIX compatibility, `fork()` (see "Process model").
- Networking, 80-column screen, graphics/GUI, sound.
- A C library for writing programs in cc65 C. Programs are assembly in v1;
  C support is a likely follow-up.
- A fast loader. Standard 1541 speed (~400 bytes/s) means a few seconds to
  load a command. Possible follow-up.
- Testing on real hardware. Target VICE only, but avoid emulator-only
  tricks so it has a fair chance on a real machine.

## Anti-goals (would be a failure even if it "works")

- Commands faked inside the shell, or output that is printed rather than
  produced by a running program.
- "Multitasking" that is really just one program at a time.
- Breaking the stock-C64 configuration in favour of REU-only features.

## Constraints

- CPU 6502 at ~1 MHz, 64 KB RAM, single hardware stack page ($0100) and
  zero page shared by everything.
- 1541 disk via the IEC serial bus: 35 tracks, 683 blocks of 256 bytes,
  ~170 KB. The drive's own DOS is flat (no subdirectories), so c64os puts
  its own filesystem on the disk (see "Filesystem").
- The C64 can only boot by `LOAD`ing a normal CBM DOS file, so the disk
  must still contain a valid CBM directory with the boot file on it.
- Toolchain (already installed on the user's Mac, user's choice to use as
  the default): ca65/ld65 (cc65 suite), c1541 for building `.d64` images,
  VICE `x64sc` for running and testing. `acme`, `dasm`, `petcat` also
  available. Build driven by a Makefile.

## Decisions made with the user

- Unix-like, real kernel, all four features (multitasking, files,
  separate executables, pipes).
- Works on stock C64 + 1541 **and** takes advantage of an REU if present.
- 6502 assembly with ca65; `.d64` output; tested in VICE.
- 40-column text console, single user, no login. (Proposed by Claude, user
  accepted.)
- **Real directories on disk** via a custom Unix-style filesystem
  (user chose this over keeping the flat CBM DOS format). The data area of
  the disk is readable only by c64os; that trade-off is accepted.

## Architecture (Claude's calls — the builder may refine)

### Memory layout (stock C64)

- BASIC ROM banked out; KERNAL ROM kept in for the IEC serial routines and
  keyboard/screen helpers where convenient.
- Kernel code and data at the top of RAM (around $C000–$CFFF, spilling
  under $A000–$BFFF as needed). Target kernel size: ≤ 8 KB.
- Process memory: the area from $0800 up to the kernel, managed in
  256-byte pages by a page allocator (~40+ KB available).
- Zero page $02–$8F (free once BASIC is out) split into a small kernel
  area plus fixed per-process slots. Stack page split into per-process
  slices, so a context switch only swaps the stack pointer and a few
  registers, not 512 bytes. Exact slot sizes are the builder's call; they
  set the process limit (expect 8).

### Process model

- Process table with: pid, parent, state (running / ready / blocked /
  zombie), memory pages, ZP slot, stack slice, fd table, exit code,
  pending signal.
- Round-robin scheduler driven by the CIA timer IRQ (hook the IRQ vector,
  keep the jiffy clock and keyboard scan running).
- **No `fork()`**: on a 6502 without relocation hardware, copying a running
  process to another address breaks its absolute addresses. Instead the
  kernel provides `spawn(path, argv, stdin, stdout, stderr)` which loads a
  program fresh and starts it (like `posix_spawn`). Plus `exit`, `wait`,
  `kill`, `getpid`, `yield`, `sleep`.
- Signals, minimal: `SIGKILL`, `SIGINT` (RUN/STOP sends it to the
  foreground process), `SIGTERM`. Default action only (terminate); no
  user handlers in v1.

### Executable format

- Programs are **relocatable**: built with ld65 in o65 format (supported by
  ld65, and the format used by earlier 6502 multitasking OSes). The kernel
  loader reads the file, allocates pages, applies relocations and starts
  the process. This lets several programs sit in memory at once at
  whatever addresses are free.
- Programs call the kernel through a fixed jump table at a known address
  (syscall number in a register or a direct `jsr` per call — builder's
  choice). Arguments arrive as argc/argv in the process's memory.

### Filesystem (c64fs)

**Hybrid disk.** One `.d64` image that is both:
- a valid CBM DOS disk whose directory (track 18) holds just the boot file
  (`C64OS`, loaded with `LOAD"*",8,1` or VICE autostart) containing the
  kernel, and
- a c64fs filesystem occupying the remaining blocks, which are marked
  allocated in the CBM BAM so the drive's DOS never overwrites them.

**On-disk layout.** Classic Unix V6/V7-style, sized for 683 blocks:
- superblock (magic, version, block/inode counts, root inode, free counts)
- block allocation bitmap
- inode table: type (file/dir), size, link count, direct block pointers
  plus one indirect block (enough for the largest file that fits on a
  1541), timestamps optional
- directories are files of fixed-size entries (e.g. 14-character name +
  inode number = 16 bytes, 16 entries per block), with `.` and `..`
- block numbers are linear and map to track/sector by the 1541 zone table

**Block access.** The kernel reads and writes raw 256-byte blocks using
the 1541's standard sector commands over the command channel (`U1` block
read, `U2` block write, `B-P` buffer pointer) on top of the KERNAL IEC
routines. No custom code is uploaded into the drive in v1. A small block
cache (a few 256-byte buffers, write-through) sits in front of it.

**Kernel features:** path lookup (absolute and relative), per-process
current directory, file create/truncate/append, `mkdir`, `rmdir`,
`unlink`, `rename` (including across directories), `stat`, `readdir`.

**Host tool: `mkfs` / image builder (Python 3).** c1541 can't write c64fs,
so the build uses a Python script that creates the hybrid `.d64`: CBM
directory + boot file, then a c64fs with `/bin` (all commands, `sh`),
`/etc` (e.g. `motd`), `/home` with a sample `readme`, and an empty `/tmp`
mount point. The same tool can list and extract files from an image, which
the automated tests use to check what the C64 wrote. Formatting a new
c64fs disk from inside c64os is a non-goal for v1.

**REU RAM disk reuses c64fs.** When an REU is present, the kernel treats it
as a second block device, formats it with c64fs at boot, and mounts it at
`/tmp`. Same filesystem code, different block driver (REU DMA).

### Files and devices

- Virtual filesystem layer with a mount table:
  - `/` → c64fs on the 1541 disk (device 8)
  - `/dev` → virtual: `console`, `null` (and room for more later)
  - `/tmp` → c64fs on the REU RAM disk when present; a plain empty
    directory otherwise
- Per-process fd table pointing at a system-wide open-file table (so
  pipes and redirected files can be shared by two processes).
- Disk driver wraps the KERNAL IEC routines. These are not reentrant and
  the serial protocol has timing windows, so disk transfers are a critical
  section: one process at a time, with task switching held off during the
  actual byte transfer. Other processes pause briefly during disk I/O on a
  stock machine — accepted.
- Console driver: keyboard input with a line discipline (cooked mode with
  line editing and echo; RUN/STOP → SIGINT), screen output with a cursor
  and scrolling.

### REU support

- Detect at boot; report size.
- RAM disk filesystem for `/tmp`, using REU DMA.
- Swapping: when a spawn can't find enough main RAM, move a blocked or
  ready process's pages out to the REU and bring them back to the same
  addresses before it runs again. This can be a later milestone than the
  RAM disk.

### Shell (`sh`)

- Reads a line, parses words, `|`, `<`, `>`, `>>`, `&`, `;`.
- Spawns each stage of a pipeline with the right fds, waits for foreground
  jobs, leaves background jobs running and reports when they finish.
- Built-ins: `cd`, `exit` only.
- Commands found by searching `/bin` (or given as a path like `./prog`).
- Prompt shows the current directory, e.g. `/home $`.

### Commands (v1)

`ls`, `cat`, `echo`, `more`, `wc`, `head`, `grep` (plain substring),
`cp`, `mv`, `rm`, `mkdir`, `rmdir`, `pwd`, `ps`, `kill`, `sleep`, `free`
(memory and REU), `df` (disk blocks/inodes free), `uname`, `clear`, plus a
`count` test program that prints a counter forever (for demonstrating
background jobs).

### Phase 2: interpreter and compiler (user asked, after the core OS)

Both are ordinary c64os programs in `/bin`, using only syscalls — no
special kernel support.

- **`basic`** — a small integer BASIC (line numbers, `PRINT`, `INPUT`,
  `LET`, `IF/THEN`, `GOTO`, `GOSUB/RETURN`, `FOR/NEXT`, `LIST`, `RUN`,
  `NEW`, `LOAD`/`SAVE` to c64fs paths). I/O through stdin/stdout, so it
  works in pipes and can run a script: `basic /home/hello.bas`.
- **`as`** — a 6502 assembler running on the C64 that reads a source file
  and writes a relocatable c64os executable, so new commands can be
  written, assembled and run entirely inside c64os:
  `as hello.s hello; ./hello`.

## What "done" looks like

Booting `c64os.d64` in VICE (stock and with `-reu`):

1. Kernel banner, memory and REU report, `$` prompt.
2. `ls` lists the disk; `cat readme` prints a file; `ls | more` pages.
3. `count > /dev/null &` then `ps` shows both processes, `kill <pid>`
   removes it.
4. `cat readme | grep unix | wc` works across three processes.
5. `echo hi > note` then `cat note` round-trips through the disk.
5a. `mkdir /home/src; cd /home/src; echo x > f; ls; cd ..; ls src` works,
    `rmdir` refuses a non-empty directory, and after a reboot the files
    and directories are still there (host tool can extract them too).
6. With REU: `ls > /tmp/x; cat /tmp/x` is near-instant; more processes
   fit before spawn fails.
7. RUN/STOP interrupts a running foreground command and returns to the
   prompt.

Automated testing: drive VICE from a host script (remote monitor / keyboard
injection and reading screen RAM) so each milestone has a repeatable check.
Builder's call how.

## Prior art the builder may study

LUnix (LNG) and GeckOS are earlier Unix-like multitasking systems for the
C64/6502 and solve the same ZP/stack/relocation problems. Study for ideas;
don't copy code.
